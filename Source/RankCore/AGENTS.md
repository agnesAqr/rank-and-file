# RankCore 작업 규칙

전투 규칙이 있는 유일한 모듈이고, 사람이 검증을 마친 커밋이 이 프로젝트의 기준이다. 같은 입력이면 어느 PC, 어느 빌드 구성에서도 같은 결과와 같은 해시가 나와야 한다. 루트와 `Source/AGENTS.md`를 먼저 읽는다.

## 결정론 점검표

코드를 고칠 때마다 전부 확인한다. 하나라도 어기면 끝난 것이 아니다.

- [ ] `float`, `double`이 없다. 비율, 평균, 보간도 여기서 계산하지 않는다
- [ ] 순서가 보장되지 않는 컨테이너(`TMap`, `TSet`)를 순회하지 않는다. 배열과 고정된 순서만 쓴다
- [ ] 포인터 주소로 비교하거나 정렬하지 않는다
- [ ] 초기화하지 않은 멤버가 없다
- [ ] 전역 변수와 정적 변수에 상태를 두지 않는다
- [ ] 한 틱 안에서 표적 선택은 틱이 시작될 때의 상태만 본다
- [ ] 엔진 난수 함수를 부르지 않는다. `Simulate` 안에는 난수가 없다. 무작위 배치를 만드는 정수 난수기는 `Simulate` 밖에서만 쓴다
- [ ] `UObject`, `UWorld`, 시각, 프레임 시간을 쓰지 않는다. `USTRUCT`, `UCLASS`, `UENUM`도 두지 않는다

`TMap`과 `TSet`의 원소 순서는 믿을 수 없고 안정적이지 않다([Epic: Map Containers](https://dev.epicgames.com/documentation/en-us/unreal-engine/map-containers-in-unreal-engine), [Epic: Set Containers](https://dev.epicgames.com/documentation/en-us/unreal-engine/set-containers-in-unreal-engine)).

## 구현의 기준

기준은 `docs/rules.md` 하나다. 기획 단계의 JS 참조 구현은 참고로 볼 수는 있지만, 결과가 JS와 같다는 것을 맞다는 근거로 쓰지 않는다. JS와 다르면 `docs/rules.md`와 손계산으로 어느 쪽이 맞는지 따지고, 정하는 것은 사람이다.

아래는 틀리기 쉬운 곳만 뽑은 것이다. `docs/rules.md`와 다르면 멈추고 알린다.

| 곳 | 지켜야 할 동작 |
|---|---|
| 유닛 생성 | 진영 0 → 1, 행 0 → 3, 열 0 → 5 순서. 유닛 번호 = 진영 × 100 + 행 × 6 + 열. 이 번호가 해시에 들어간다 |
| 링크 | 상하좌우 이웃의 병과가 다르고 그 병과에 링크 효과가 있을 때 한 겹. 종류마다 세 겹까지. 사거리는 최대 4, 간격은 최소 4틱, 체력은 한 겹에 +5 |
| 첫 공격 | 대기 시간의 처음 값은 간격이다. 첫 공격은 간격 번째 틱에 나간다 |
| 사거리 밖 | 대기 시간이 0이 됐는데 대열 순번이 사거리 이상이면 0에 머문 채 기다린다. 대기 시간을 다시 채우지 않는다 |
| 순회 | 의도 수집과 사망 정리 모두 진영 0 → 1, 열 0 → 5, 대열 앞 → 뒤 순서다 |
| 표적 고정 | 의도를 모을 때 고른 표적을 적용할 때 바꾸지 않는다. 그 틱에 이미 체력이 0 이하가 된 표적에도 피해와 이벤트를 그대로 적용한다 |
| 지원 표적 | 마주 보는 열이 비면 거리 1부터 5까지, 같은 거리에서는 왼쪽 열을 먼저 본다. 모두 비면 성문 |
| 범위 표적 | 왼쪽, 가운데, 오른쪽 순서로 각 열의 맨 앞. 셋 다 비면 성문을 한 번만 친다 |
| 피해 | 물리는 max(1, 공격 − 방어), 마법은 공격 값 그대로, 성문은 성문 피해 값 |
| 부활 | 체력을 부활 값으로 바꾸고 부활 값을 0으로 한다. 자리는 그대로다. 부활 이벤트만 내고 사망 이벤트는 내지 않는다 |
| 빈 틱 | 의도가 하나도 없는 틱에는 적용, 사망 정리, 판정을 건너뛴다 |
| 판정 | 성문이 0 이하이거나 모든 열이 비면 그쪽이 진다. 양쪽이 같은 틱에 지면 무승부(Draw)다. 600틱까지 끝나지 않으면 Timeout이고 틱은 600으로 기록한다 |
| 해시 | FNV-1a 32비트. 시작값 `0x811c9dc5`, 곱하는 수 `0x01000193`. 정수 하나는 하위 바이트부터 4바이트를 차례로 XOR하고 곱한다. `uint32` 곱셈의 넘침을 그대로 쓴다 |
| 해시에 섞는 순서 | 성문 타격: 틱, 1, 공격자 번호, 999, 피해. 피해: 틱, 2, 공격자 번호, 표적 번호, 피해. 부활: 틱, 3, 유닛 번호. 사망: 틱, 4, 유닛 번호. 끝날 때: 마지막 틱, 결과 코드(A 1, B 2, Draw 3, Timeout 4). 이벤트 로그도 같은 종류 값과 필드를 쓴다 |
| 플레이어 기준 판정 (`Judge`) | A 승: 승리, 결계가 0 이하면 결계 파괴, 아니면 섬멸. Timeout: 승리, 새벽. Draw: 성문이 남아 있으면 승리(성문 사수), 아니면 패배(성문 붕괴). B 승: 패배, 성문이 0 이하면 성문 붕괴, 아니면 전멸 |

## 공개 형태

- `Rank::Simulate(const FBattleInput&, bool bRecordLog)`는 입력만으로 결과가 정해진다. 전역 상태를 읽거나 쓰지 않는다. 로그를 기록하든 안 하든 결과와 해시가 같아야 한다.
- `Rank::ComputeLinks`는 전투와 배치 화면이 함께 쓴다. 링크 식을 두 곳에 두지 않는다.
- `Rank::Judge`는 코어 결과를 플레이어 기준 승패와 종류(섬멸, 결계 파괴, 새벽, 성문 사수, 성문 붕괴, 전멸)로 바꾼다.
- `FFormationMask::CanPlace`는 행마다 비트 6개로 점유를 검사한다. 칸 단위로 단순하게 짠 판정을 지우지 않는다. 등가성 테스트(T4)의 대조군이다.
- 병과 능력치와 규칙 매개변수는 입력으로 받는다. 이 모듈의 코드에 적지 않는다.
- 무작위 배치를 만드는 함수와 정수 난수기는 하나만 두고 테스트, BalanceSim, RankGolden이 함께 쓴다. 방식은 11/17 확정(`docs/design.md` 9.3): 분대 순서를 섞고 분대마다 회전과 위치를 40번까지 시도한다. 하나라도 못 놓으면 그 배치를 버리고 처음부터 다시 한다(최대 100번). 100번 안에 못 만들면 실패로 알린다. 분대를 빼고 넘어가지 않는다.
- 공개 구조체나 함수의 모양을 바꾸면 `RankGame`, `RankEditor`, `RankTests`가 함께 바뀐다. 바꾸기 전에 알린다.

## 기준으로 확정하는 절차

아래 네 가지가 모두 끝나야 기준이 된다. 4번은 사람만 한다.

1. 손계산 시나리오(T5)가 전부 통과한다. 기대값은 AI가 규칙 문서로 계산하고 사람이 확인한 값이다.
2. 결정성(T2) 1,000/1,000, 미러(T3) 1,000/1,000, 배치 판정 등가성(T4) 10,000/10,000.
3. 사람이 코드를 `docs/rules.md`의 조항과 위의 결정론 점검표에 대조해 리뷰했다. AI는 조항별로 해당 코드의 파일과 줄을 정리한 대조표를 만들어 리뷰를 돕는다.
4. 사람이 `docs/decisions.md`에 "RankCore 기준 확정"을 커밋, 통과한 테스트 수, 리뷰한 범위와 함께 적는다.

확정 직후 `tools\record_golden.bat`으로 골든 벡터 20건(T1)을 기록한다. 그 뒤로 T1은 회귀 테스트다. 확정 전에는 골든 벡터를 기록하지 않는다.

## 테스트가 실패했을 때

- 손계산 시나리오(T5)가 어긋나면: 이벤트 로그를 한 줄에 하나씩 뽑아 시나리오에 적힌 계산 과정과 틱 단위로 대조하고, 처음 갈라지는 틱과 단계(의도 수집, 적용, 사망 정리, 판정)를 보고한다. 계산이 틀렸는지 코드가 틀렸는지는 사람이 정한다. 규칙 문서가 모호해서 생긴 차이면 문서를 먼저 고친다.
- 골든 벡터(T1)가 어긋나면: 의도하지 않은 동작 변경이다. 바뀐 대전 가운데 이벤트 수가 가장 적은 것을 골라, 기록 당시 커밋과 지금 커밋의 이벤트 로그를 나란히 놓고 처음 다른 틱을 찾는다. 원인을 찾기 전에는 다른 작업으로 넘어가지 않는다.
- 의도한 변경(사람이 승인한 규칙·수치 변경, 사람이 확인한 버그 수정)이면 바뀐 대전 목록을 보이고 승인을 받은 뒤 다시 기록한다. 기대값을 손으로 고치지 않는다.

## 특성과 유물

처리 시점과 조각 수가 정해지지 않았다(`docs/design.md` 6.8절, 15절). 사람이 정하기 전에는 구현하지 않는다. 구현할 때는 조각마다 AI가 계산하고 사람이 확인한 예제를 2개 이상 테스트로 두고(T7), 특성이 들어간 덱으로 결정성과 미러 테스트를 다시 돌린다. 동작이 바뀌는 것이므로 골든 벡터 다시 기록도 승인을 받는다.
