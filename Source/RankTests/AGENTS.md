# RankTests 작업 규칙

테스트는 통과시킬 대상이 아니라 규칙을 강제하는 검사기다. 기대값은 사람이 확인한 계산값, 성질(결정성, 대칭), 사람이 검증을 마친 `RankCore`의 기록 가운데 하나에서만 온다. 루트와 `Source/AGENTS.md`를 먼저 읽는다.

## 테스트 목록

| ID | 테스트 | 기대값의 출처 | 통과 기준 |
|---|---|---|---|
| T1 | 골든 벡터: 대전 20건을 돌려 기록과 비교 | 기준으로 확정된 `RankCore`가 `tools\record_golden.bat`으로 남긴 기록 | 결과, 틱, 이벤트 수, 해시가 20/20 일치 |
| T2 | 결정성: 무작위 대전 1,000판을 두 번씩 돌린다 | 성질 | 해시 1,000/1,000 일치 |
| T3 | 미러: 무작위 배치 1,000개를 자기 자신과 붙인다 | 성질 | 1,000/1,000 무승부(Draw 또는 Timeout) |
| T4 | 배치 판정 등가성: 비트마스크 판정과 칸 단위 판정을 무작위 1만 건으로 비교 | 칸 단위 판정 | 10,000/10,000 일치 |
| T5 | 손계산 시나리오: 작은 대전의 끝 틱, 승패, 성문 값, 지정한 유닛의 체력 | AI가 규칙 문서로 계산, 사람이 확인 | 전부 일치 |
| T7 | 특성 조각: 조각마다 예제 2개 이상 | AI가 규칙 문서로 계산, 사람이 확인 | 전부 일치 |
| T8 | 콘텐츠: 채택본 JSON이 관문 1을 통과하고 DataTable 행 수와 같다 | JSON | 탈락 0, 행 수 일치 |
| T9 | 런 스모크: 탐색 봇이 시드 10개로 런을 끝까지 돈다. 같은 시드를 두 번 | 성질 | 멈춤과 크래시 0, 같은 시드는 같은 결과 |
| T10 | 재생 일치: 재생이 끝난 화면 상태와 `FBattleResult` 비교 | `FBattleResult` | 일치 |

- T6(JS 참조 구현과 승률 비교)은 2026-11-17에 없앴다. 번호는 다시 쓰지 않는다.
- 이름은 `RankAndFile.Core.*`, `RankAndFile.Content.*`, `RankAndFile.Run.*`로 나눈다. `tools\run_tests.bat`이 `RankAndFile` 전체를 돌린다.
- `IMPLEMENT_SIMPLE_AUTOMATION_TEST`로 쓴다. T1~T5는 화면 없이 돈다.
- `RankCore`가 기준으로 확정되기 전에는 T1의 기록 파일이 없다. 그때 T1은 "기준 확정 전"이라는 메시지로 실패한다. 건너뛰거나 통과로 처리하지 않는다.

## 손계산 시나리오 (T5)

- 파일은 `Fixtures/hand_v1.json`이다. 시나리오마다 id, 가리키는 조항 번호, 양쪽 진형, 계산할 항목, 기대값, 계산 과정, 확인 상태를 둔다.
- 파일에 계산할 때 쓴 병과 수치와 규칙 매개변수의 해시를 넣는다. 지금 데이터의 해시와 다르면 "수치가 바뀌어 다시 계산해야 한다"로 실패한다. 병과 수치가 확정되기 전에는 계산을 시작하지 않는다.
- 기대값은 AI가 계산하고 사람이 확인한다.
  - AI는 `docs/rules.md`의 조항만 보고 계산한다. `RankCore`나 JS 참조 구현의 코드를 보거나 실행해서 값을 얻지 않는다. 구현을 맡은 세션과 다른 세션에서 계산하는 것을 권한다.
  - 계산 과정을 틱 단위로 적는다: 그 틱에 공격하는 유닛, 표적, 피해, 남은 체력, 쓰러짐과 부활, 판정. 사람이 줄마다 따라가며 확인할 수 있어야 한다. 과정 없이 결과만 적은 기대값은 쓰지 않는다.
  - 계산하다 규칙이 모호한 곳을 만나면 짐작으로 정하지 않는다. 그 시나리오를 멈추고 모호한 조항을 알린다.
- 확인 상태는 `확인 전` 또는 `본인 확인(날짜)`이다. `본인 확인`은 사람만 적는다.
- 기대값이 없거나 `확인 전`인 시나리오는 "본인 확인 전"으로 실패한다. 건너뛰지 않는다.
- 테스트가 어긋났을 때 AI가 자기 계산이 틀렸다고 판단하면, 고친 계산 과정과 이유를 내고 상태를 `확인 전`으로 되돌린다. 사람이 다시 확인하기 전에는 통과로 보지 않는다.
- 조항마다 시나리오가 하나 이상 있어야 한다. 특히 처리 순서와 경계값이 갈리는 곳: 사거리 밖 대기 뒤의 첫 공격, 같은 틱의 동시 사망, 해골 졸개의 부활, 지원 표적의 왼쪽 우선, 범위 표적이 성문을 한 번만 치는 경우.

## 무작위 입력

- T2, T3, T4의 무작위 배치는 시드를 고정한 정수 난수기로 만든다. JS의 난수기와 무작위 배치 함수를 옮기지 않는다. 실수 연산을 쓰기 때문이다.
- 실패 메시지에 시드와 몇 번째 입력인지 넣는다. 그 입력 하나만 다시 돌릴 수 있어야 한다.

## 금지

- 기대값(해시, 틱, 이벤트 수, 승률, 손계산 값)을 고쳐서 통과시키지 않는다.
- 테스트를 끄거나, 건너뛰거나, 판 수를 줄이지 않는다(1,000 → 100, 20 → 19).
- 허용 오차를 넣지 않는다. 정수와 해시의 비교는 정확히 같아야 한다.
- 실패를 "알려진 실패"로 분류해 빼지 않는다.
- `Fixtures/golden_v1.json`을 손으로 고치지 않는다. `tools\record_golden.bat`으로만 만들고, 다시 기록은 사람이 승인했을 때만 한다(`Source/RankCore/AGENTS.md`).
- 구현을 돌려서 나온 값을 손계산 시나리오나 특성 예제의 기대값으로 삼지 않는다.

## 기록 파일

- `golden_v1.json`에는 기록한 커밋, 병과 수치와 규칙 매개변수의 해시가 들어 있다. 테스트는 시작할 때 지금 데이터의 해시와 비교하고, 다르면 "기록이 지금 수치와 다르다"는 메시지로 실패한다. 조용히 통과하거나 건너뛰지 않는다.
- 수치나 규칙이 바뀌면 영향을 받는 손계산 시나리오를 AI가 다시 계산하고 사람이 확인하고, 승인을 받아 골든 벡터를 다시 기록하고, `docs/design.md`의 골든 벡터 표를 맞춘다.

## 실패했을 때

- 그대로 보고한다: 테스트 이름, 처음 어긋난 항목(시드, 틱, 이벤트 번호), 기대값과 실제값.
- 이어서 할 일은 `Source/RankCore/AGENTS.md`의 "테스트가 실패했을 때"를 따른다.
- 테스트가 틀렸다고 판단되면 고치지 않고 근거와 함께 알린다. 테스트를 고치는 일은 사람이 승인한다.

## 테스트를 더할 때

- 버그를 고치면 그 버그를 잡는 테스트를 함께 넣는다. 고치기 전에 실패하고 고친 뒤에 통과하는 것을 확인한다. 새 테스트의 기대값도 사람이 확인한다.
- 무작위 입력을 쓰는 테스트는 시드를 고정하고 시드를 실패 메시지에 넣는다.

## 보고 형식

```
T5 12/12 · T2 1,000/1,000 · T3 1,000/1,000 · T4 10,000/10,000 · T1 20/20(기준 확정 뒤)
명령: tools\run_tests.bat · 빌드: Development Editor · 커밋: abc1234
```

실행된 테스트가 0개면 통과가 아니다. 테스트를 돌리지 못했으면 돌리지 못했다고 적는다.
