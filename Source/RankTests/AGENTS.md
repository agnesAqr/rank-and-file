# RankTests 작업 규칙

테스트는 통과시킬 대상이 아니라 규칙을 강제하는 검사기다. 기대값은 교차 검증에서 일치했거나 사람이 판정한 계산값, 성질(결정성, 대칭), 사람이 검증을 마친 `RankCore`의 기록 가운데 하나에서만 온다. 루트와 `Source/AGENTS.md`를 먼저 읽는다.

## 테스트 목록

|---|---|---|---|

- `RankCore`가 기준으로 확정되기 전에는 T1의 기록 파일이 없다. 그때 T1과 T11은 "기준 확정 전"이라는 메시지로 실패한다. 건너뛰거나 통과로 처리하지 않는다.

## 손계산 시나리오 (T5)

- 파일은 `Fixtures/hand_v1.json`이다. 시나리오마다 id, 가리키는 조항 번호, 양쪽 진형, 계산할 항목, 기대값, 계산 과정, 확인 상태를 둔다.
- 파일에 계산할 때 쓴 병과 수치와 규칙 매개변수를 `Data/defs/units.csv`, `rules.csv`와 같은 열 이름과 값으로 그대로 옮겨 넣는다. 테스트는 지금 `Data/defs`의 값과 하나씩 비교하고, 다르면 어긋난 병과와 값을 적고 "수치가 바뀌어 다시 계산해야 한다"로 실패한다. 병과 수치가 확정되기 전에는 계산을 시작하지 않는다.
- 기대값은 AI가 계산하고, 다른 회사 모델이 따로 계산해 비교한다(교차 검증, 2026-11-20 결정). 두 계산이 다른 시나리오만 사람이 본다. 절차는 `docs/crosscheck/README.md`, 검증자에게 주는 지시는 `docs/crosscheck/hand_v1/INSTRUCTIONS.md`다.
  - AI는 `docs/rules.md`의 조항만 보고 계산한다. `RankCore`나 JS 참조 구현의 코드를 보거나 실행해서 값을 얻지 않는다. 구현을 맡은 세션과 다른 세션에서 계산하는 것을 권한다.
  - 계산 과정을 틱 단위로 적는다: 그 틱에 공격하는 유닛, 표적, 피해, 남은 체력, 쓰러짐과 부활, 판정. 두 계산이 다를 때 사람이 줄마다 따라가며 판정할 수 있어야 한다. 과정 없이 결과만 적은 기대값은 쓰지 않는다.
  - 계산하다 규칙이 모호한 곳을 만나면 짐작으로 정하지 않는다. 그 시나리오를 멈추고 모호한 조항을 알린다.
- 교차 검증
  - 검증자는 기대값을 계산한 모델, `RankCore`를 구현한 모델과 다른 회사의 모델이다. `docs/rules.md`와 눈가림 입력(`docs/crosscheck/hand_v1/inputs.json`: 병과 수치, 규칙 매개변수, 양쪽 진형)만 보고 처음부터 계산한다. 기존 기대값, 계산 과정, 시나리오의 목적, `Source/`의 코드, 테스트 결과를 보여 주지 않는다. 기존 계산을 검토시키지 않는다.
  - 비교는 `node tools/hand_crosscheck.js compare`로만 한다. 검증자에게 비교 결과를 알려 주고 답을 고치게 하지 않는다. 다시 계산시킬 때는 새 대화와 새 실행 폴더에서 같은 지시문으로 한다. 받은 실행은 모두 남긴다.
  - 두 계산이 다르거나, 검증자가 모호하다고 표시했거나, 검증자가 허용 목록 밖의 파일을 열었으면 사람이 판정한다. AI는 판정하지 않고 보고서(`report.md`)만 만든다. 다수결로 정하지 않는다.
  - 구현을 맡은 세션은 비교의 개수, 시나리오 id, 어긋난 항목 이름만 다룬다. 기대값과 보고서의 값을 열어 보지 않는다.
  - 검증자의 결과와 검증자가 짠 프로그램은 기준이 아니다. 기대값과 다른 곳을 찾는 데만 쓴다.
- 확인 상태는 `확인 전`, `교차 확인(모델, 날짜)`, `본인 판정(날짜)`, `본인 확인(날짜)` 가운데 하나다. `교차 확인`은 `tools/hand_crosscheck.js apply`만 적는다(비교한 항목이 전부 일치한 시나리오). `본인 판정`은 달랐던 시나리오를 사람이 기존 기대값이 맞다고 판정했을 때, `본인 확인`은 사람이 계산 과정을 직접 확인했을 때 쓴다. 둘 다 사람이 말했을 때만 옮겨 적는다.
- 기대값이 없거나 `확인 전`인 시나리오는 "확인 전"으로 실패한다. 건너뛰지 않는다.
- 테스트가 어긋났을 때 AI가 자기 계산이 틀렸다고 판단하면, 고친 계산 과정과 이유를 내고 상태를 `확인 전`으로 되돌린다. 다시 교차 검증에서 일치하거나 사람이 판정하기 전에는 통과로 보지 않는다.
- 조항마다 시나리오가 하나 이상 있어야 한다. 특히 처리 순서와 경계값이 갈리는 곳: 사거리 밖 대기 뒤의 첫 공격, 같은 틱의 동시 사망, 해골 졸개의 부활, 지원 표적의 왼쪽 우선, 범위 표적이 성문을 한 번만 치는 경우, 가장자리 열의 범위 공격이 성문을 치는 경우, 넘친 피해와 음수 성문 값, 빈 진영의 입력 오류(§3.6).

## 회귀 테스트 입력 (T1, 11/18)

- 입력은 `Fixtures/regression_branches.csv`(갈래 목록)로 고른다. 열은 `id,clause,branch,static,tests,battles,detect`다. `static`은 배치만 봐도 그 갈래를 지나는지 아는지(`TRUE`/`FALSE`), `tests`는 맡는 테스트(`;`로 잇는다), `battles`는 지날 대전 id(`;`로 잇는다. `전부`는 모든 대전, `실전`은 rb10~rb20), `detect`는 확인 방법이다.
- 갈래는 `docs/rules.md`의 조항과 §9에서 뽑는다. 떠올린 것으로 채우지 않는다. 조항을 바꾸면 목록도 같은 변경 안에서 맞춘다.
- `tests`에 T1이 있는 갈래는 대전 1건 이상이 지나야 한다. `static`이 `FALSE`인 갈래는 초안에서 보장되지 않는다. RankCore를 구현한 뒤 첫 기록 전에 RankRegression의 갈래 집계로 확인하고, 0건이면 입력을 고친다(승인).
- 기준 확정 전에 변이 검사를 한다(`docs/design.md` 9.5): `docs/rules.md` §9에서 고르지 않은 선택지 8개를 하나씩 넣은 임시 코드로 T1과 T5를 돌려, 변이마다 하나 이상이 실패해야 한다. 변이 코드는 커밋하지 않는다.
- 로그 체크섬은 이벤트 로그의 모든 줄의 다섯 칸(틱, 종류, 행위자, 표적, 값)을 순서대로 `docs/rules.md` §6과 같은 FNV-1a 방식으로 섞은 값이다. 규칙의 해시(§6)와는 따로 테스트 쪽에서만 쓴다.

## 무작위 입력

- T2, T3, T4의 무작위 배치는 시드를 고정한 정수 난수기로 만든다. JS의 난수기와 무작위 배치 함수를 옮기지 않는다. 실수 연산을 쓰기 때문이다.
- 실패 메시지에 시드와 몇 번째 입력인지 넣는다. 그 입력 하나만 다시 돌릴 수 있어야 한다.

## 금지

- 기대값(해시, 틱, 이벤트 수, 승률, 손계산 값)을 고쳐서 통과시키지 않는다.
- 테스트를 끄거나, 건너뛰거나, 판 수를 줄이지 않는다(1,000 → 100, 20 → 19).
- 허용 오차를 넣지 않는다. 정수와 해시의 비교는 정확히 같아야 한다.
- 실패를 "알려진 실패"로 분류해 빼지 않는다.
- `Fixtures/regression_battles_v1.json`을 손으로 고치지 않는다. `tools\record_regression.bat`으로만 만들고, 다시 기록은 사람이 승인했을 때만 한다(`Source/RankCore/AGENTS.md`).
- `Fixtures/regression_inputs.csv`(회귀 테스트 입력)는 사람이 승인했을 때만 고친다. 입력을 바꾸면 결과도 다시 기록한다.
- T1은 입력 CSV를 `RankGame`의 변환 함수로 읽는다. 테스트 안에 따로 만들지 않는다.
- `Fixtures/regression_branches.csv`(갈래 목록)도 사람이 승인했을 때만 고친다.
- T11의 Shipping 결과로 기록 파일을 만들거나 고치지 않는다. T11이 어긋났다는 이유로 다시 기록하지 않는다.
- 구현을 돌려서 나온 값을 손계산 시나리오나 특성 예제의 기대값으로 삼지 않는다.
- `hand_v1.json`의 확인 상태를 손으로 `교차 확인`으로 고치지 않는다. `tools/hand_crosscheck.js apply`로만 적는다.
- 검증자의 결과 파일(`docs/crosscheck/**/result.json`)과 비교 보고서를 고치지 않는다. 다시 받을 때는 새 실행 폴더에 받는다.

## 기록 파일

- `regression_battles_v1.json`에는 기록한 커밋, 그리고 병과 수치와 규칙 매개변수가 `units.csv`, `rules.csv`와 같은 열 이름과 값으로 들어 있다. 테스트는 시작할 때 지금 `Data/defs`와 하나씩 비교하고, 다르면 어긋난 값을 적고 "기록이 지금 수치와 다르다"로 실패한다. 조용히 통과하거나 건너뛰지 않는다.
- 수치나 규칙이 바뀌면 영향을 받는 손계산 시나리오를 AI가 다시 계산하고 교차 검증을 다시 하고(눈가림 입력을 다시 만든다), 승인을 받아 회귀 테스트 결과를 다시 기록하고, `docs/design.md`의 회귀 테스트 표를 맞춘다.

## 실패했을 때

- 그대로 보고한다: 테스트 이름, 처음 어긋난 항목(시드, 틱, 이벤트 번호), 기대값과 실제값.
- 이어서 할 일은 `Source/RankCore/AGENTS.md`의 "테스트가 실패했을 때"를 따른다.
- T11이 어긋나면 빌드 구성에 따라 결과가 달라지는 결정론 버그다. 어긋난 대전 가운데 이벤트 수가 가장 적은 것을 골라 에디터와 Shipping 패키지의 이벤트 로그를 나란히 놓고 처음 다른 틱을 찾는다. 원인은 `Source/RankCore/AGENTS.md`의 결정론 점검표로 좁힌다.
- 테스트가 틀렸다고 판단되면 고치지 않고 근거와 함께 알린다. 테스트를 고치는 일은 사람이 승인한다.

## 테스트를 더할 때

- 버그를 고치면 그 버그를 잡는 테스트를 함께 넣는다. 고치기 전에 실패하고 고친 뒤에 통과하는 것을 확인한다. 새 테스트의 손계산 기대값도 같은 교차 검증을 거친다.
- 무작위 입력을 쓰는 테스트는 시드를 고정하고 시드를 실패 메시지에 넣는다.

## 보고 형식

```
T5 12/12 · T2 1,000/1,000 · T3 1,000/1,000 · T4 10,000/10,000 · T1 20/20(기준 확정 뒤)
명령: tools\run_tests.bat · 빌드: Development Editor · 커밋: abc1234
T11 20/20 · 명령: tools\check_shipping_determinism.bat · 빌드: Shipping · 커밋: abc1234
T5 교차 검증 일치 18/18 · 검증자: Antigravity <모델> · 명령: node tools/hand_crosscheck.js compare <결과 파일>
```

실행된 테스트가 0개면 통과가 아니다. 테스트를 돌리지 못했으면 돌리지 못했다고 적는다.
